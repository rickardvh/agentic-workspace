# Preserve a working rule where it will be used

Use this reference when configuring assistance for an evidenced repository
convention or applying an enduring correction. Establish the smallest useful rule
and show that a later consumer encounters it before the dependent action. Stop
when that connection works; no new module, record or helper is required by default.

## Start from the repository's actual method

Read the existing instruction, command or script and the user's intent. Determine
what must hold, when it matters, which action depends on it, how to establish it
cheaply and what would invalidate reuse. These are reasoning questions, not a
required file format. A rule to read a contract may need only a sentence and link.

A filename is a discovery hint, not authority for a command, working directory,
dependency group, environment or network operation. Resolve ordinary choices from
current evidence. If a convention could mean two materially different procedures,
name the missing decision and affected action; continue independent work. Preserve
exclusions and settled choices, including unchanged deferred decisions.

Prefer making an existing test/build command establish its own prerequisites.
For example, normal `uv run` synchronises its project environment; inspect the
actual flags and supported tool version (`--no-sync` changes that behaviour).
Do not add a separate install before an already self-preparing command. `npm ci`
replaces `node_modules`; it is preparation, not a cheap read-only readiness probe.
Follow the repository's supported invocation, rather than choosing an ecosystem
default from these examples.

## Connect the rule to its consumer

Merge or reference adequate existing instructions and build/test skills. Publish
managed instructions through [instruction publication](../../workspace-instruction-correction/references/instructions.md).
Ordinary repository instructions, scripts and skills use the authorised repository
editing workflow. Put reusable methods in the repository's established skill
location, separate from installed AW skills. A short conditional instruction is
often enough; use a skill/helper only when repeated procedure work justifies it.
Planning and Memory are optional. Standing Verification requirements can maintain
repository conditions; they cannot certify another checkout's installed dependencies.

Choose an already-used build/test skill, applicable instruction or existing
activity/semantic route that reaches the consumer **before** its action. Preserve
stronger explicit timing rules. Separate applicability from freshness: a lockfile
may invalidate preparation while the task edits source, and tests may need it with
no edits. A lockfile-only path scope misses those consumers. Do not invent changed
paths or assume `use` or `checks` is a pre-command hook. Optional advice supplies
no execution permission or task-wide gate.

For a repository whose documented test command is `uv run --locked python -m
unittest discover -s tests`, a compact rule in its existing always-read repository
instructions can say:

> For Python tests, use the documented command from the project root. It prepares
> the project environment before testing. If preparation fails, report the missing
> prerequisite and do not report tests as having run. Unrelated work needs no
> environment preparation.

Use this only when those are the target's actual conventions. If a longer method
is necessary, link its repository-owned skill from that conditional instruction.
Keep the rule and recovery readable without AW, especially when AW itself uses
the environment needing repair. That fallback grants no unavailable AW authority.

## Check only what the action needs

Reuse sufficient current observations. Prefer a supported tool-owned check, a
cheap relevant observation, or the established safe preparation when checking
separately costs more. Unknown readiness is not failure and does not authorise a
reinstall. Missing tools, access, network or policy should yield a scoped explanation
of the prerequisite and affected action, without routine approval requests.

Compare bounded inputs only when a known successful result is reusable and the
comparison avoids more expensive work. Use a verified public convenience tool or
owner revision where available; otherwise an available host tool under the skill's
contract. Internal Rust hashing functions are not public commands. Declare the
consistent byte representation and hash only material inputs, not the whole
repository or installed dependency tree.

Matching inputs do not establish that preparation succeeded or its outputs remain.
Relate any reusable observation to the actual successful operation, its options,
material manifests/toolchain/configuration and the environment/output consumed.
Missing or recreated environments, deleted generated files and observed external
mutation defeat reuse. An unchanged service configuration does not establish a
running service: observe live readiness near use. Hashes and TTLs cannot replace
that observation.

Prefer tool-owned state. If a concrete helper needs a disposable local stamp,
name its writer, exact checkout/environment subject, validity limits and removal
behaviour in that helper's skill. Store it only in the established ignored output
or cache directory as bounded replaceable procedure output. Never share it as
machine-independent truth or add Configuration/Verification fields, a generic
registry or per-run history. Removal means unknown readiness and the supported
recheck/preparation path, not AW bookkeeping recovery. Local success is operational
evidence, not authenticated proof or independent review.

A helper must not publish success after failure, uncertain interruption or inputs
changing during preparation. Invalidate prior reusable success before replacing
its subject; use existing tool coordination when needed. Do not infer surviving
outputs from a digest alone. A stateless or tool-native method needs no stamp.

## Verify the connection and stop

Give a fresh consumer an ordinary relevant task and repository state, without the
author's chat or hints about changed inputs. Observe its action order and outcome,
including a no-edit test/build task. Check current reuse, a changed governing input,
missing output/environment and failed or uncertain preparation. Contrast an
unrelated task and a self-preparing command; review generated-output deletion and
stopped-service readiness only when those distinctions matter to the method.

Quiet when current means no redundant preparation, repeated question, durable
write, full runbook delivery or unrelated probe. A static conditional instruction
may still be read. Reuse current context; a new session alone does not require a
command. Report the observed result and exact gaps, not universal enforcement.
