## Package and host exposure

Use the current `setup_context` request and supply the requested `job`:
`refresh-payload`, `expose-skill`, `expose-plugin`, `configure-behavior`,
`assess-setup` or `remove-adoption`. For behavior or assessment, also supply the
relevant `concern` and `scope` (`repository` or `machine-local`). The selected
view gives only that job's current choices. Carry its exact reference with
current reentry and the bounded answer through the
[owner interaction procedure](../../workspace-startup/references/owners.md).
Selection grants no write authority; invoke only the admitted action.

For refresh, use the exact changed-file or recovery choice. Existing setup
choices remain in place; package-byte refresh does not require another feature
audit. Unchanged reviewed setup stays quiet. For host exposure, choose the
named skill or plugin's expose, remove or recovery request. Follow any returned
plugin host-cache steps explicitly. Collisions and unsupported hosts remain gaps.

If setup returns `custody_recovery.condition: local-adoption-custody-absent`,
inspect its `status`, `gaps` and `artifact_hint`. A fresh checkout can contain the
old package files without the local record required to replace them. The hint
does not authenticate a former package. Establish its matching distribution or
source independently through the repository's trusted installation route. Run
that artifact with the returned `prior_setup.arguments`; authorise its normal
setup only if the preview accepts the files without tracked package changes.
Then use the selected new artifact with `resume.arguments`, authorise the exact
refresh and confirm a second preview is `already-current`. Preserve disabled AW
and local/domain state. If the former artifact is unavailable, or either preview
finds edits, an unknown fence or changed policy, report that exact gap. Do not
download or execute an unverified former binary, copy local records, infer
permission from portable hashes, or use `--recover` for absent history.

For assessment, answer the selected concern's question: what changed, what
actually works, and what remains with another owner. Supply `judgment` and
`reason`, plus `resume` naming the owner and next action for unfinished work.
Use `working` only for an observed supported consumer; `handled-by-owner` keeps
diagnostics, Assignment, modules and launch readiness with their actual owners.
Configuration supplies current source bindings, observations and the complete
record internally. It still validates them before publication. Add explicit
`dependencies` only for repository sources that informed this judgment.

Read `setup_result`: the committed effect, actual consumer verification and
remaining owner gaps are separate facts. A missing consumer check remains
unresolved. Setup consideration supplies no module, Assignment, machine or task
readiness. After an interrupted committed effect, use exact reentry or recovery;
preserve the effect and never replay it to obtain a missing observation.

Removal preserves custom policy, notes, plans and optional domain state. Remove
authenticated host exposures first when required. Domain-state disposition needs
that owner's authority and the user's intent. Sibling repositories remain outside
the target.

Only for a development source checkout or a returned source reassessment gap,
use [source-checkout preparation](source-checkout.md). Installed consumer setup
needs no maintainer build or regeneration recipe.

Detailed assessment records, consumer witnesses, provenance and preservation
diagnostics remain available through lazy `configuration_write` detail and its
current requests. Load them for an actual diagnosis or source-authoring concern,
then resume the original task. Optional unresolved setup blocks its dependent
claim; it does not prevent unrelated authorized work.
