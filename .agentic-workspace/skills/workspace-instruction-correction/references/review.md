# Review retained knowledge for useful improvements

Use when the user requests a repository-improvement review. Start from what the
repository and its components already know; the user need not nominate a finding.
Agree on a bounded subject from the request and current repository intent. A
repository-wide request permits selective discovery, not an exhaustive health claim.
Keep the result in the response or existing work owner; create no report archive.

## Select evidence before diagnosing

Use sufficient current context already available. When current owner information
is missing, follow [ordinary entry](../../workspace-startup/references/ordinary.md)
with the actual review task. Inspect returned source references, owner context and
exact `detail_refs` for the question being considered. Follow an owner's returned
read/query request through [owner carriage](../../workspace-startup/references/owners.md).
Select activities by meaning through the current semantic-route selection request;
do not invent changed files to recall advice or make task prose a runtime classifier.

For orientation beyond the currently selected task, use the repository's
`.agentic-workspace/READING.json` and its `.agentic-workspace/OWNERSHIP.toml`
source at the same revision. Check their source blob relationship as described in
[source reading](../../workspace-startup/references/unavailable.md). Choose relevant
entries by their concern, refs and owner; follow exact references and declared
dependencies. If necessary, enumerate only a named immediate directory to choose
a relevant source. Do not walk archives, private runtime storage or every owner.
This profile supplies source-reading routes, not current executable authority.
An unavailable profile leaves directly identified sources usable with stated limits.

Where available, consider at least two different source-owner classes whose
evidence could change the same repository outcome. For example, compare a retained
intent interpretation with a scoped instruction, advisory workaround or proof gap.
These are examples, not a required module list. Use the selected owners' current
requests when current admission, source state or effects matter. Direct reads of
declared source material can establish observations, not owner admission.
An absent/disabled owner or unavailable runtime is a coverage limit, never proof
that no improvements exist. Follow the same bounded source-reading path when AW
is unavailable and leave native custody, permissions and effects unknown.

Read canonical code, docs, rules or checks implicated by those observations under
the [evidence rules](../../workspace-startup/references/evidence.md). Record exact
file/section or request references, revisions, scope and dependencies. Separate
observed behavior, retained assertions and your inference. Source hashes establish
identity; recorded confidence, repetition and interpretation do not establish truth.
Changed or unsupported advice cannot govern a repair. Check counterevidence and
legitimate version/environment/scope differences before declaring a conflict.

## Make a small set of supported decisions

Group symptoms only when current evidence supports a shared underlying cause or
simplification. Explain that relationship; several warnings alone do not prove it.
Keep genuinely independent issues and unresolved facts distinct. Consider positive
opportunities, such as eliminating repeated work or a compensating method, even
when no test fails. Stop optional collection when it cannot change the disposition;
preserve required coverage and disclose material unknowns.

For each worthwhile result, tell the maintainer:

- what was observed, its exact evidence and currentness, and what remains inference;
- which repository behavior or imminent decision it affects and why it matters;
- the smallest proposed change, controlling source and owner, scope and confidence;
- expected future benefit and present implementation/proof/maintenance cost, with
  estimates labelled and unmeasured payoff left unknown;
- the constructible next action, current constraints and proportionate proof.

Use one coherent proposal for related symptoms, not an issue per observation.
State which owners/sources were considered. A justified no-action result says why
no worthwhile change was demonstrated within that coverage; it does not certify
the whole repository. Already-owned work keeps its existing issue or Planning
owner. Hypotheses, stale evidence and distinct human-owned choices stay explicit.

## Advance the selected result

Use [initiative latitude](opportunity.md) and the [destination procedure](destination.md)
for the current proposal. A review request authorises investigation; it does not
itself authorise every suggested write. Effective latitude selects proposal,
report or no-action; publication still needs the destination's authority. Keep
reporting-only review read-only. Ask only for an owner-required bounded human
decision, not approval of semantic inference or an unavailable capability.

For an authorised code/doc/method correction, name the exact source change and
check its resulting bytes and behavior. For managed sources, answer and invoke
the current owner's exact request/action. For unfinished legitimate work, use the
repository's existing issue procedure or
[Planning intake](../../../planning/skills/planning-work/references/intake.md),
carrying the outcome, source evidence, scope and proof; confirm the saved work.
Filing work establishes a route, not a repaired repository. A defer/no-action
result names the reason and any affected action; it creates no suppression record.

After a correction, verify the controlling source and use its owner's fresh view.
Follow [destination reconciliation](destination.md) for affected projections and
superseded advice; preserve independent evidence, rationale and unresolved work.
Do not advance hashes or statuses just to silence pressure. Finish with the
confirmed effect or owned next step and its honest remaining limits.
