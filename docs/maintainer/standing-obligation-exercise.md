## Current assurance model: fresh exercises

After external review, the lifecycle was redesigned around
`assurance.requirements` with `requirement_class = "current-evidence"`.
Three new agents independently received only their fixture root and the task
“Report whether this repository needs attention using its current procedures.”
They followed root AGENTS.md without implementation sources, earlier outputs or
follow-up hints. Fixture names exposed the control category; this was not blind.
Each fixture included startup/setup guidance, reporting latitude and a copied
native launcher/core pair. Narrow fixture delegation and synthetic semantic
assessment established the satisfied starting point, not native command proof.

| Fixture | Observed behavior | Friction and changes |
| --- | --- | --- |
| Due | Found `--result` in the interface and stale `--output` in the example; reported the due requirement and its completion restriction. Submitted the finding without treating it as admitted evidence. | An optional missing local config caused one combined read to fail. | Satisfied | Reused `current-authorised-assessment` without reopening the usage procedure or reassessing it. | Tried an incomplete owner identity before forwarding the exact Configuration request. No changes. |

All three correctly kept the separately unassessed Configuration integration
unfinished. In the satisfied and absent cases, Configuration detail returned
about 17,327 tokens and exceeded the reader's output budget; neither claimed to
have completed that assessment. No user intervention was needed for the reporting
task. No agent reviewed or approved a PR. These are partial fixture repositories,
not evidence of complete installed-package integration or hosted scheduling.

## Historical peer-registry exercises

The following observations predate the assurance redesign. They explain the
detail-reference and optional-section fixes, but do not establish behavior of
the repaired lifecycle. The fresh exercises above supply its behavioral evidence.

### Setup and task

Four fresh agents received only an assigned fixture root and the task:
“Report whether this repository needs attention using its current procedures.”
The prompt did not name the usage obligation, its procedure or a check command.
Agents were told to follow that root's AGENTS.md and avoid the implementation,
other fixtures and earlier exercise outputs. Fixture directory names indicated
their control category, so this was not a blinded comparison.

Each fixture carried a native launcher/core pair and repository-owned startup
guidance. The repository's reporting latitude limited handling to reporting.
The usage procedure compared a documented option against `interface.json`.
Synthetic setup evidence and a narrowly scoped fixture delegation established
initial satisfaction; this was not production command proof.

The due fixture then changed the supported option from `--output` to `--result`.
The example and evidence still named `--output`. Controls kept the matching
assessment or declared no obligation. These were partial repositories, not a
claim about complete installed-package integration.

| Exercise | Result | Calls and friction |

Kept the obligation unresolved after supplying the finding and respected reporting latitude. | Four native calls within eight shell calls. All commands succeeded; one truncated read was repeated with enough output budget. A temporary context file was created and removed. |

Initial fixtures lacked setup guidance and agents reported that separate gap.
The final fixture included it. Configuration integration remained unassessed and
was correctly kept separate from permission to report the usage mismatch. No
agent received a follow-up hint or requested user intervention. None reviewed or
approved a PR.

The stale-reference reports exposed a runtime defect: read-only assessment request
templates included the current second, changing optional-detail references while
sources were unchanged. Templates now omit observation time; an assessment
supplies the time of its actual observation. The native test holds a detail
reference across a second boundary and then resolves the same detail successfully.

The exercises also exposed a runtime/schema inconsistency: a valid standalone
obligation manifest was treated as invalid because optional proof sections were
absent. Present malformed sections remain invalid; absent optional sections no
longer create that false gap.

## Mechanical evidence and limits

The detail-route review correction separates `freshness.procedure` from the
existing evidence-detail route. The native lifecycle/entry case now runs with
both `measurement:latency` and a pytest command as `detail_route`, while activation
routes to `procedure.md`. Both forms retain publication, quietness, recovery and
portable-currentness coverage. The fresh-agent observations above preceded this
field separation; the regression checks establish the corrected routing contract.

The native lifecycle test covers exact publication, protected writes, failed
recovery after evidence changes, successful recovery without republishing,
replacement currentness and retirement preserving evidence. It now also compares
ordinary CLI and external JSON activation, verifies satisfied/removal quietness,
and copies only repository sources to a second checkout before detecting drift.
This is transport and checkout evidence, not an executed hosted schedule or a
second operating system.

Focused Rust tests cover expiry, failed/unknown outcomes, changed policy and
evidence, exact/delegated authority, latitude clamping and quiet controls. Adding
200 unrelated files preserves the obligation read set; no broad scan or check is
introduced. Existing activation and optional-detail tests retain their own
semantics and scaling controls.

The current assurance implementation passes the mechanical checks described
above and has fresh due, satisfied and absent behavioral observations. No token-cost improvement,
independent acceptance or complete configuration integration is claimed.
