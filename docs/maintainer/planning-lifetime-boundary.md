# Planning lifetime boundary

Planning retains durable work meaning. Current PR, review, CI, issue, provider and
integration observations do not become tracked feature-branch authority.

## Classification

New native Planning creation requires an explicit material_lifetimes declaration.
The current owner classifies the historically mixed slots; native code never
guesses from their prose:

| Slot | Classification | Durable representation |
| --- | --- | --- |
| next_action | durable or observation | Preserve durable work; observation becomes an empty required-schema slot |
| relationships.external_posture | observation | Omit from durable material and current subject projection |
| continuation.frontier | durable or observation | Preserve accepted semantic meaning; omit operational frontier text |
| Other continuation, intent, scope, constraints, dependencies and proof obligations | durable | Preserve in full |
| Returned / integration-pending / assignment custody | existing typed owner lifetime | Preserve; classification cannot edit or waive these owners |

Legacy records without a declaration retain their unknown meaning. The public
lifetime projection labels this as unclassified legacy and grants no external
authority. A current owner may classify legacy slots during an admitted semantic
update, preserving accepted progress and residual obligations. This is not an
automatic migration or a requirement to refresh a feature when external state
moves.

New declared observations are projected out before persistence. Repeated material
submissions whose only differences are observations return unchanged and no
Planning action: no revision increment, postimage or bookkeeping commit.

A real change to durable meaning still requires an exact admitted update.
Physical source revisions, invocation custody and postimage checks remain exact;
semantic lifetime filtering never authorizes stale source or operation replay.

## Returned work

The handoff and result owners may need a new custody postimage even when semantic
material is unchanged. Their private update path preserves this distinction; no
caller-controlled force-write switch exists.

Adoption retains an accepted result in continuation.frontier when that slot is
durable. When frontier is classified as an observation, the exact returned
request names continuation.accepted_progress instead. An identical summary does
not eliminate the need to consume a new admitted return or clear its pending
handoff. Fresh consumers retain the accepted result and all remaining obligations.

## Current external and target posture

Review, CI, issue and provider observations must be obtained from their current
owners at use time. A stored external_posture object is never a current external
oracle. Losing observations or local presentation carriage cannot lose durable
work meaning.

An optional owner-scoped integration_proposal retains only a target ref,
requested transition, proof references and remaining obligations. It contains no
moving target HEAD or integrated-status mirror.

Native Planning can lazily observe this proposal on its declared Git target.
The observation checks the current branch and immutable HEAD, requires the exact
live owner bytes to be present in that commit, and checks the branch/HEAD again
before returning. Missing Git, detached state, a different branch, absent or
different committed owner bytes, and target movement remain unproven. No plan,
receipt, tracker or feature branch is written by this observation.

integration-observed proves bounded inclusion only. An explicit current owner
request may then apply the matching proposed lifecycle change through the existing
Planning update operation. The request cannot simultaneously change the integrated
semantic work, substitute a proposal or act on a feature branch. The returned
action binds the observed ref/HEAD and exact owner source; normal invocation
re-entry and final publication revalidation reject target movement.

Owner lifecycle disposition remains separate from task completion. Git inclusion
and a closed owner grant neither proof nor task-completion authority. Existing
Verification/source/claim restrictions and residual obligations remain intact;
there is no merged=true or passing-command shortcut.
## Validation

The public lifetime fixture exercises native, JSON, Python and TypeScript:
lower review/CI/head/merge and provider/issue observations move without changing
upper tracked Planning bytes; actual residual meaning changes require an update;
fresh processes recover accepted progress and residual obligations; exact target
inclusion is derived without an AW commit; committed-source mismatch and missing
Git remain unproven; an explicit matching target-local lifecycle update preserves the independent task-completion boundary.

Existing creation/reconciliation fixtures cover explicit legacy classification,
portable source custody, stale requests and interrupted update recovery. The
handoff fixture additionally covers an already-retained summary in the durable
accepted-progress slot and the separate consumption receipt.

The implementation uses the current native Planning create/update/reconciliation
owners and their existing custody store. It adds no global event ledger, tracker,
session authority, branch rewrite service or former Python execution fallback.
