# Extension boundary

[Choose a rule, skill, helper or module](customization.md) with the receipt-format example.

Modules add domain capability; skills describe reusable method; repository
instructions carry repository policy. They have separate authority and lifecycle.

The supported executable extension path is the [native module contract](module-capability-contract.md).
A linked Rust owner describes its domain and resolves bounded observations. The
repository separately admits its revisions, source reads, effects and claim scope.
There are no mandatory workflow phases, act/reconcile callbacks or skill hooks.
Read-only owners need no fake state or publication. Independent modules do not
require core owner-name switches; see the separately assembled neutral fixture.

An optional ordinary or AW-assisted skill uses the same passive registry and
relative resources as host skills. Generic procedure answers are caller-owned
semantic input, not authority. Native owners still validate facts, restrictions,
publication and proof when skills are absent. Skills are not executable modules.

Repository customization uses current config, scoped Markdown instructions,
canonical source decisions, ownership, proof declarations and host skills.
External adapters consume the same native start/invoke transport; they own vendor
integration and credentials, not repository policy, proof or completion authority.
No adapter registry, marketplace or generic workflow engine is implied.

Current public Python/TypeScript bindings transport the native contract. Historical
Python module entry points, module-capability/v2 and source-maintenance lifecycle
metadata do not define an installed alternative host. Compatibility precedes
contribution; unadmitted, incompatible, conflicting or unavailable capability stays
explicit. Removal cannot make cached contributions authoritative or destroy foreign
state. Source-owned facts stay with their owner rather than a central context store.

First-party Planning, Memory and Verification demonstrate domain custody, advisory
knowledge and evidence ownership. Their optional method is now narrow selected
references. Native support still requires actual owner implementation, separate
admission, bounded sources, current results and appropriate proof. Passing a fixture
does not establish every platform, lower operating cost or release acceptance.
