# Current host feasibility: #3383

The original machine-local configuration declared Astra, Sol, Terra and Luna as
`internal` targets with binding `required-best-fit` and automatic transport.
For `unapplied-patch`, only the current Astra target was constructible. The old
owner could admit local execution without resolving Sol's missing host binding.
This reproduces the issue; that original local admission did not establish a
complete host comparison.

The implementation keeps otherwise admissible non-current internal declarations
unknown. They must be bound to a supported concrete transport in source policy.
The supported sealed Codex bridge now supplies a bounded, fresh capability
observation before comparison. Its protocol/model and adapter revisions enter the
configuration identity and are checked again at dispatch. No static flag grants
constructibility, and no worker turn runs during discovery.

The current Windows host's installed app-server discovery listed all four
configured models and supported fresh turns and medium reasoning effort. The
machine-local Sol, Terra and Luna declarations were changed to explicit sealed
bridge commands using this checkout's actual Python interpreter. Target identities,
priors, prohibitions and Assignment policy were preserved. Dynamic target fields
are source configuration; the current bounded Configuration writer does not expose
those fields. No interpreted Assignment state was edited.

An ordinary native startup with the same implementation requirement then showed
`codex_sol:native:codex-app-server/v1` as authorized, safe, constructible and
eligible for `read-only` and `unapplied-patch`. The host observation was available.
Terra and Luna were excluded by the acting judgment that their source prohibitions
apply to this boundary-changing task. The current comparative judgment selected
Astra for architecture, integration and proof work, considering Sol as a feasible
alternative and the cost of transferring the coupled change. That is a task
judgment, not a measured economic result or unconditional preference for local work.

The regression uses a controlled adapter through all four current consumers:
native CLI, JSON, Python and TypeScript. It proves unknown internal binding blocks
local admission, concrete available binding admits non-local selection and reaches
the exact dispatch frontier, known unavailability permits local comparison, and
unknown discovery or changed capability/configuration requires re-resolution.
Retained-local and command-safety controls do not probe. The existing sealed host
handoff fixture covers actual dispatch, return admission, Planning and proof
boundaries; its matrices were reused rather than copied.

Validation also found stale source-maintenance checks from the preceding command
cleanup: operation migration-status expectations, an obsolete packed Node import,
and a native transport fixture missing its now-required command. Those checks now
exercise the current boundaries. A test-fixture ordering error left command safety
disabled before its unavailability check; restoring the source between scenarios
resolved it. These were test failures, not successful first-pass evidence.

The new path is supported through the concrete bridge, not a direct mapping to
Codex conversation subagent tools. Actual host discovery was exercised; no paid
worker turn or completion-cost benchmark was run. Provider failure remains an
execution outcome and cannot become proof of target quality or issue completion.
Implementation is offered for independent review; this report is not a PR review,
approval, merge, or release verdict.
